# 项目总纲：astrbot_plugin_prompt_preset（提示词条目编排插件）

> 项目：AstrBot 插件——让用户像 SillyTavern 预设那样自由添加提示词条目，完全控制所有提示词的发送顺序、角色与内容。
> 本文件是项目的**单一事实源**。所有设计决策、技术调研结论、任务书进度都在这里。
> 创建：2026-09-08　状态：M1 任务书已定稿，待交付 zcode。

---

## 0. 一句话定位

完全接管 AstrBot 的 LLM 请求组装：把 persona、对话历史、自定义文本全部变成"条目"，每条有排序权重和角色，用户按任意顺序排列组合，插件按排序结果重建最终发给 LLM 的 messages 列表。

## 1. 起源与需求（主人原话的 distilled）

主人（驱蚊花露水/水煮冰糕）发现 AstrBot 回复有 AI 味——思考链太短、说话像客服、role play 完全不对味。排查后发现根源：AstrBot 的 persona 只是"静态描述"（是什么、不许什么），**没有告诉模型怎么思考**，模型的思考链按训练默认模式走（解题式分析），和 role play 不搭。

解法是在 persona 末尾嵌入思考框架指令（①身份→②意图→③心情→④措辞），让模型按框架展开思考链。但手工改 persona 不可持续——需要**一个能自由添加/排序/开关提示词条目的插件**，让用户随时调整发给 LLM 的每一句话。

主人的核心要求（原话 distilled）：
1. **高度自由化**：不要固定模式、不要预设模板、不要"推荐配置"。条目想怎么组合怎么组合。
2. **顺序完全自由**：persona 可以放最前也可以放最后，对话历史同理。
3. **role 完全开放**：system/user/assistant 每条独立设。
4. **不要复杂化**：不做 WebUI、不做 ST 导入、不做预设模板。命令 + JSON 就够。
5. **独立插件**：和 astrbot-living（自主生活）正交，受众更广。

## 2. 与 astrbot-living 项目的关系

- **完全独立的两个项目**：prompt-preset 管"提示词怎么组装"，astrbot-living 管"闲时自主生活"。互不依赖、可共存。
- 技术栈共享：同为 AstrBot 插件，共享开发流程（任务书→zcode→凛核验）和 VM 测试环境。
- astrbot-living 的 M2 思考框架需求（persona 末尾加思考步骤指令）可由此插件的条目实现——但 astrbot-living 不依赖本插件。

## 3. 技术调研结论（2026-09-08 源码核实）

### 3.1 AstrBot LLM 请求管线

```
用户消息 → AstrBot pipeline → 组装 ProviderRequest:
  req.system_prompt = AstrBot 系统提示 + persona(经 _ensure_persona_and_skills 注入)
  req.contexts = 对话历史(含 LivingMemory fake messages)
  req.tools = FunctionTool 集
→ 插件钩子 call_event_hook(OnLLMRequestEvent, req) ← 各插件可修改 req
→ openai_source._query(payloads) → HTTP POST 到 LLM API
```

### 3.2 关键源码坐标

| 事实 | 位置 |
|---|---|
| 钩子注册 | `astrbot/core/star/register/star_handler.py` → `register_on_llm_request()` |
| 钩子调用 | `astrbot/core/pipeline/context_utils.py` → `call_event_hook(event, EventType.OnLLMRequestEvent, req)` |
| 钩子遍历 | `astrbot/core/star/star_handler.py` → `get_handlers_by_event_type()` 按 `self._handlers` 注册顺序遍历，**无优先级机制** |
| persona 注入 | `astrbot/core/astr_main_agent.py` → `_ensure_persona_and_skills()`：`req.system_prompt += f"\n# Persona Instructions\n\n{prompt}\n"` |
| persona 读取 | `context.persona_manager.get_default_persona_v3(umo)` → `Personality` TypedDict（`prompt` 字段） |
| LivingMemory 记忆注入 | `data/plugins/astrbot_plugin_livingmemory/core/event_handler_modules/memory_recall.py`：`req.contexts.extend(fake_messages)`（伪工具调用消息对） |
| persona 存储 | `data/data_v4.db` → `personas` 表（persona_id='凛'，system_prompt 1133 字符） |

### 3.3 钩子执行顺序与策略

钩子按 `self._handlers` 注册顺序执行 = 插件加载顺序（目录名字母序）。LivingMemory（l）在本插件（p）之前执行。

**策略**：不依赖钩子顺序。预设插件在钩子里拿到的是组装完成的完整 `req`（含 persona 和 LivingMemory 的 fake messages），在这份成品上做**定位重建**——用条目列表决定最终顺序。LifeMemory 的 fake messages 已在 contexts 里，chat_history 条目展开时自然包含它们。

### 3.4 depth 注入可行性

`req.contexts` 是 `list[dict]`（OpenAI 格式消息），任意位置 `insert()` 可行。LivingMemory 自己就在往里 `extend()`，结构已验证。

### 3.5 思考强度调研（顺带核实）

AstrBot 内置思考配置：`gm_thinking_config`（Gemini）、`anth_thinking_config`（Claude）、`reasoning_effort`（OpenAI 兼容，默认 high）。但**实测**（2026-09-08）：主人的中转站模型（glm-5.3-flash/qwen-3.8-flash）**默认就带思考链**（1427/712 字），加不加参数差别不大——回答质量问题不在思考量，在 prompt 引导方向。

## 4. 核心数据模型（定稿）

### 条目（Entry）

```json
{
  "order": 0.0,
  "role": "system",
  "source": "text",
  "content": "【思考框架】① 回到身份：我是凛……② 理解主人的意图……",
  "enabled": true,
  "name": "思考框架"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| order | float | 排序权重，升序。浮点数可插任意间隙。必填 |
| role | string | `system` / `user` / `assistant`。默认 system |
| source | string | `text` / `persona` / `chat_history`。默认 text |
| content | string | 条目内容（source=text 时生效；支持变量替换） |
| enabled | bool | 开关。默认 true |
| name | string | 条目名（管理用，不发给 LLM） |

### source 类型

| source | 内容来源 | 说明 |
|---|---|---|
| `text` | content 字段 | 自定义文本，支持变量替换 |
| `persona` | AstrBot 当前人格全文 | 从 persona_manager 取 |
| `chat_history` | 对话历史 | req.contexts 原样（含 LivingMemory fake messages） |

### 组装算法

`on_llm_request` 钩子触发时：

1. 读取启用的条目，按 order 升序
2. 收集原材料：persona_text（persona_manager）、chat_history（req.contexts 原样）
3. 逐条生成消息：
   - source=text → 变量替换 content → 按 role 生成消息
   - source=persona → persona_text 作 content
   - source=chat_history → 展开 req.contexts 原始消息（保持原始顺序）
4. **完全接管**：第一条 role=system 的消息拼入 req.system_prompt，其余写入 req.contexts
5. 条目列表为空或全 disabled → 不做任何操作（保留 AstrBot 原生行为）

### 变量系统

| 变量 | 展开为 |
|---|---|
| `{{persona}}` | AstrBot 当前人格全文 |
| `{{user_name}}` | 配置中的用户名 |
| `{{bot_name}}` | 配置中的机器人名 |
| `{{time}}` | HH:MM |
| `{{date}}` | YYYY-MM-DD |
| `{{datetime}}` | 日期+时间 |

未知变量保留原样（不替换不报错）。

## 7. 与 LivingMemory 的兼容性

- **不 fork、不 import** LivingMemory（AGPL 隔离，同 astrbot-living 项目）。
- LivingMemory 在自己的钩子里通过 `req.contexts.extend(fake_messages)` 注入记忆——本插件完全接管后，chat_history 条目展开时自然包含这些 fake messages（记忆不丢）。
- 钩子执行顺序（LivingMemory 先于本插件，字母序 l < p）不影响功能：本插件拿到的是组装完成的成品，重排后发出。
- **硬约束**：不修改 LivingMemory 任何文件，不 import 其源码（AGPL）。
